# Sendina — Монетизатор

Рабочая основа продукта по предоставленному ТЗ: русско-английский интерфейс, кампании, адресаты, предпросмотр писем, учёт ответов, домены, журнал, защитные правила и MCP для управления из ChatGPT.

**Это версия 0.1, а не завершённая автономная система 100/100.** Данные на стартовой панели — явно обозначенные примеры. Реальная отправка отключена. Внешнее исследование, автоматический поиск контактов и обработка входящей почты пока не подключены.

## Сайт

https://annetbg-wq.github.io/sendina/

GitHub Pages обслуживает интерфейс, API развёрнут на Railway: https://sendina-production.up.railway.app

Рабочая область защищена токеном: на первом экране нужно ввести `APP_TOKEN` сервера. Токен хранится только в sessionStorage вкладки. Кнопка «Посмотреть демонстрацию» переводит браузер в демонстрационный режим без сервера — данные сохраняются в localStorage только текущего устройства. Вернуться к серверу можно на экране «Настройки». API и MCP нельзя запустить на GitHub Pages.

## Локальный запуск

Требуется Node.js 24.

```sh
npm ci
npm run dev
```

Интерфейс: http://127.0.0.1:5173. API: http://127.0.0.1:3001.

```sh
npm test
npm run build
npx playwright install chromium
npm run test:e2e
npm run test:e2e:gate
```

На Windows можно использовать установленный Edge: `$env:PLAYWRIGHT_CHANNEL='msedge'` перед браузерными тестами. Тесты API используют отдельный временный каталог; браузерные тесты — `data/e2e` и отдельные порты.

## Данные и доступ

- Без `DATABASE_URL` сервер хранит состояние атомарно в `data/state.json`; это режим одного процесса.
- При `DATABASE_URL` используется PostgreSQL: состояние рабочей области хранится в JSONB с транзакционной блокировкой. Нормализованная схема и многопользовательская изоляция относятся к следующему этапу.
- По умолчанию API слушает loopback. Публичный адрес включается только вместе с `APP_TOKEN`: без токена сервер не стартует. Для внешнего доступа задайте `ALLOWED_ORIGINS=https://annetbg-wq.github.io`; см. «Сервер на Railway».
- Пользовательский токен UI хранится только в sessionStorage. OAuth-токены MCP не сохраняются в данных.
- Не добавляйте `.env`, токены, реальные адресаты и содержимое `data/` в репозиторий.

## MCP / ChatGPT

Endpoint: `POST /mcp`, транспорт Streamable HTTP. Инструменты:

| Инструмент | Назначение |
|---|---|
| `get_dashboard` | Показатели и готовность системы |
| `list_campaigns` | Список кампаний |
| `list_opportunities` | Демонстрационные гипотезы |
| `get_campaign` | Кампания, адресаты, письма, ответы |
| `create_campaign` | Создание черновика |
| `import_contacts` | Импорт с дедупликацией |
| `preview_campaign` | Черновики и решения по правилам |
| `set_campaign_status` | Изменение состояния кампании |
| `emergency_stop` | Остановка или снятие остановки |
| `exclude_recipient` | Глобальное исключение адресата |

Для локального MCP-клиента задайте `MCP_TOKEN` и передавайте `Authorization: Bearer …`. Это тестовый режим, не законченная авторизация для ChatGPT.

Для подключения через ChatGPT:

1. Разверните Node API за HTTPS. GitHub Pages остаётся адресом интерфейса.
2. Настройте OAuth 2.1 authorization server с PKCE и регистрацией клиента ChatGPT.
3. Задайте `MCP_RESOURCE_URL`, `OAUTH_ISSUER`, `OAUTH_JWKS_URL`, `MCP_SUBJECT` и `APP_TOKEN` в окружении сервера.
4. Access token должен содержать корректные `iss`, `aud` (точно `MCP_RESOURCE_URL`), `exp`, `sub` (точно `MCP_SUBJECT`) и `scope`: `sendina:read` / `sendina:write`.
5. Добавьте HTTPS MCP endpoint в ChatGPT по актуальной инструкции ниже. Само подключение к аккаунту ChatGPT в этой версии не выполнялось.

Сервер публикует OAuth protected resource metadata на `/.well-known/oauth-protected-resource/mcp`, проверяет JWT через JWKS и ограничивает рабочую область одним заранее привязанным субъектом. Собственный OAuth authorization server не реализован: используется внешний провайдер. Инструменты имеют read/write-аннотации; изменения проходят через тот же API, что и UI.

Официальные источники: [MCP server](https://developers.openai.com/plugins/build/mcp-server), [authentication](https://developers.openai.com/plugins/build/auth), [connect ChatGPT](https://developers.openai.com/plugins/deploy/connect-chatgpt).

## Реализованные сценарии

- Создание кампании с контекстом, рынком и обязательным целевым событием.
- Импорт JSON-адресатов: email, имя, компания, источник, основание, конкретная причина контакта. Повторный импорт не создаёт дубль в кампании.
- Предпросмотр первых пяти писем; повторный запрос не создаёт дубликаты черновиков. Текст составляется из введённых фактов, без заявления о работе ИИ.
- Ручная регистрация ответа через API; повтор `eventId` не дублирует событие. Отписка и отказ создают глобальное исключение.
- Проверки остановки, состояния кампании, исключения, наличия ответа, основания контакта, домена и общего лимита. Все предпросмотры получают версию решения и причину блокировки.
- Реальная проверка наличия SPF, DKIM и DMARC через серверный DNS. Наличие записей не делает домен автоматически готовым к отправке.
- Аварийная остановка. Её снятие не возобновляет кампании автоматически.
- RU/EN для экранов, форм и уведомлений; язык сохраняется, пользовательские тексты не переводятся.
- Вход по токену для защищённой рабочей области, переключение языка прямо на экране входа и переход в демонстрацию без сервера.

## Что ещё требуется по полному ТЗ

SMTP/API-адаптер и очередь с защитой от повторной отправки; автоматическое получение ответов; модели и строгие схемы ИИ-результатов; исследование с источниками; автоматический поиск контактов; версионированные правила юрисдикций; динамические лимиты по репутации; оркестрация экспериментов и перераспределение объёма; подтверждённые доставки и ценность результата; полноценные workspace/RBAC, OAuth provisioning и нормализованная БД.

Сейчас `/api/send` всегда возвращает 409. Это явная граница реализации, а не имитация доставки.

## Сервер на Railway

GitHub Pages отдаёт только интерфейс. Проверка DNS, MCP и общая рабочая область требуют Node-сервера.

1. Railway → **New Project** → **Deploy from GitHub repo** → `annetbg-wq/sendina`. Файл `railway.json` задаёт сборку, запуск и проверку `/api/health`.
2. Добавьте в проект **PostgreSQL**. Railway сам подставит `DATABASE_URL`. Без него состояние лежит в файловой системе контейнера и пропадает при каждом развёртывании.
3. Переменные сервиса:

   | Переменная | Значение |
   |---|---|
   | `APP_TOKEN` | случайная строка; без неё сервер откажется слушать публичный адрес |
   | `ALLOWED_ORIGINS` | `https://annetbg-wq.github.io` |
   | `DATABASE_URL` | подставляет Railway |

   `PORT` и `HOST` задавать не нужно: `PORT` приходит от Railway, а публичный адрес включается по `RAILWAY_ENVIRONMENT_NAME`.
4. **Settings → Networking → Generate Domain**. Получится адрес вида `https://sendina-production.up.railway.app`.
5. В GitHub: **Settings → Secrets and variables → Actions → Variables** → `VITE_API_URL` = адрес из шага 4 (уже задан). Переменная читается при сборке, поэтому после её изменения нужен новый запуск workflow «Deploy GitHub Pages». Это переменная сборки, она попадает в браузер — секреты в неё класть нельзя.
6. Откройте сайт, на экране «Настройки» введите `APP_TOKEN`. Токен хранится только в sessionStorage вкладки.

Без `VITE_API_URL` сайт остаётся демонстрацией в браузере: данные не покидают устройство, проверка DNS и MCP недоступны. Сохранённый в браузере адрес сервера имеет приоритет над `VITE_API_URL`; пустое значение выбирает демонстрационный режим.

## Публикация

Workflow `.github/workflows/pages.yml` проверяет тесты, собирает приложение с `/sendina/` в качестве base path и публикует `dist` через GitHub Pages. Необязательная repository variable `VITE_API_URL` задаёт адрес отдельного API. Секреты нельзя помещать в переменные `VITE_*`: они попадают в браузер.

[GitHub Pages deployment documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
