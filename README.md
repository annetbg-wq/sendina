# Sendina — Монетизатор

Рабочая основа продукта по предоставленному ТЗ: русско-английский интерфейс, исследование возможностей и рынков, кампании, адресаты, предпросмотр писем, ветки переписки, аналитика за период, домены и почта, журнал, защитные правила и MCP для управления из ChatGPT.

**Версия 0.2.** Новый аккаунт получает пустую рабочую область: никаких демонстрационных кампаний, ответов, рынков и показателей. Демонстрация — отдельный режим, который включается и очищается вручную. Реальная отправка по-прежнему отключена: её открывают проверенный ящик, версионированные правила и подтверждение первой партии.

## Сайт

https://annetbg-wq.github.io/sendina/

GitHub Pages обслуживает интерфейс, API развёрнут на Railway: https://sendina-production.up.railway.app

Вход — по одноразовой ссылке на рабочий адрес; пароля нет. Новому адресу доступ открывает суперадмин. Кнопка «Посмотреть демонстрацию» переводит браузер в демонстрационный режим без сервера — данные сохраняются в localStorage только текущего устройства. API и MCP нельзя запустить на GitHub Pages.

Интерфейс работает из трёх мест одинаково: с GitHub Pages (API на другом источнике), с самого Railway (страницу и API отдаёт один сервер) и локально. Адрес API определяется один раз: сохранённый выбор → адрес из сборки → собственный источник, если он отвечает на `/api/health` → демонстрация.

## Локальный запуск

Требуется Node.js 24.

```sh
npm ci
npm run dev
```

Интерфейс: http://127.0.0.1:5173. API: http://127.0.0.1:3001.

```sh
npm test                     # ядро, правила, аккаунты, MCP, источник запроса
npm run build
npx playwright install chromium
npm run test:e2e             # интерфейс в браузерной демонстрации
npm run test:e2e:gate        # экран входа на собранном приложении
npm run test:e2e:product     # сквозные сценарии против настоящего сервера
npm run test:e2e:gate
```

На Windows можно использовать установленный Edge: `$env:PLAYWRIGHT_CHANNEL='msedge'` перед браузерными тестами. Тесты API используют отдельный временный каталог; браузерные тесты — `data/e2e` и отдельные порты.

## Аккаунты и доступ

Вход без пароля: адрес → письмо со ссылкой → сессия. Новый аккаунт получает доступ только после подтверждения одним из суперадминов.

Суперадмины по умолчанию: `vkdevproai@gmail.com`, `oopsifymovie@gmail.com`, `pavekornilov@gmail.com`. Дополнительные задаются переменной `SUPERADMINS`. Суперадмин подтверждён автоматически и входит без ожидания.

- **У каждого аккаунта своя рабочая область.** Кампании, адресаты, письма, ответы, домены, ящики и журнал разделены полностью: в PostgreSQL это отдельная строка `workspace_state` на аккаунт, в файловом режиме — отдельный файл.
- **Суперадмин управляет людьми, а не их данными.** На экране «Аккаунты» он видит список адресов, подтверждает и блокирует их. Чужие кампании, адресаты и почтовые токены ему недоступны — это проверяется тестом.
- Суперадмина нельзя заблокировать. Блокировка обычного аккаунта немедленно закрывает его сессии.
- Ссылка для входа одноразовая и живёт 20 минут. Она уходит только на почту: в ответе API её нет никогда.
- Сессия хранится в localStorage браузера и действует `SESSION_DAYS` дней (по умолчанию 30).

### Первый вход

Пока `SYSTEM_SMTP_*` не заданы, письма отправлять нечем. В этом случае суперадмин — и только он — может запросить вход, и ссылка запишется в журнал сервера (`[sendina] login link for …`). Доступ к журналу и так означает доступ к серверу, поэтому это не расширяет права. Обычный пользователь в таком состоянии получит честный отказ.

## Навигация

**Главная · Рассылки · Возможности · Рынки · Ответы · Аналитика · Настройки.**

«Домены и почта» переехали внутрь «Настроек» отдельным подразделом — экран не изменился, изменилось только его место. «Аккаунты» видят только суперадмины: меню собирается по роли, а не показывает недоступный пункт, и все маршруты за ним отказывают обычному пользователю независимо от меню.

Настройки разделены на подразделы: **Почта и домены · Интеграции · Запрещённые адресаты · Рабочая область · Сервер приложения.** Адрес сервера, служебные токены и состояние хранилища видит только суперадмин.

## Возможности

Один внутренний механизм Opportunity Research, доступный из интерфейса, из MCP и платформенной модели. Пользователь задаёт страну, регион или город, направление и, если нужно, короткое дополнительное условие — всё необязательно. Система возвращает **ровно шесть** актуальных возможностей; каждая содержит название, суть, для кого, почему сейчас, почему эта локация, предполагаемый чек, сложность реализации, сложность продажи, конкуренцию, правовой риск, оценку 0–100 с объяснением и время исследования.

Оценку считает не модель, а `server/research.ts`. Модель возвращает десять факторов от 0 до 10; оценка выводится из них по логике ТЗ — боль × срочность × готовность платить × доступность покупателей × преимущество от ИИ × рынок, делённое на сложность реализации × сложность продажи × конкуренцию × правовой риск. Буквальное отношение неограниченно, поэтому обе стороны сворачиваются средним геометрическим, а сторона сложности применяется как штраф: каждый фактор двигает оценку в ту сторону, которую задаёт ТЗ, и результат всегда укладывается в шкалу, которую показывает интерфейс. Объяснение оценки собирается из самих факторов, поэтому не может разойтись с числом рядом.

Две кнопки на карточке: **создать тест** — обычная кампания через существующее ядро, **в избранное** — сохранить. Результаты поиска не сохраняются сами: следующий поиск заменяет текущие шесть, избранное остаётся.

## Рынки

Тот же механизм, три явных режима на одном экране:

| Режим | Вопрос | Ответ |
|---|---|---|
| У меня есть страна | территория задана | шесть самых перспективных ниш для неё |
| У меня есть ниша | ниша задана | шесть самых перспективных стран или регионов |
| Оценить моё сочетание | заданы обе | только оценка этой пары, без альтернатив |

Третий режим — это то, что делает ИИ помощником, а не обязательным источником решения: оператор всегда может назвать ответ сам и попросить только мнение. Карточка та же, «Подготовить тест» создаёт обычную Campaign — отдельной market-модели нет.

## География

Страны больше не заданы статически. `server/geo.ts` — единственный источник и для интерфейса, и для операций: около сотни стран с ISO-кодом и регионом, семь регионов. Кампания или поиск могут указать одну страну, несколько, регион, город — или оставить выбор Sendina, и это осознанный ответ, а не пустое поле. Названия стран в англоязычном интерфейсе берутся из того же модуля, поэтому селектор и словарь не могут разойтись.

## Ответы

Одна свёрнутая карточка на адресата. В свёрнутом виде: адресат, организация, последний ответ, дата, классификация, текущий статус, рекомендуемое следующее действие и отметка, выполнено ли оно. По клику раскрывается вся ветка — наше письмо, ответ, следующее письмо и так далее, с датой, направлением, темой, текстом, решением системы и следующим действием на каждом шаге. Итог ветки (встреча назначена, документы получены, интерес, позже, отказ, отписка, недоставка, другой) показывается отдельно от классификации последнего письма и редактируется вручную.

Ветки собираются из строк, которые рабочая область уже хранит: исходящие — это письма кампании, входящие — её ответы. Единственное новое поле — отметка о выполнении следующего действия. «Исключить адресата» — то же глобальное исключение, что и раньше; отказ и отписка по-прежнему блокируют будущую отправку автоматически.

## Аналитика

Два фильтра решают всё, что показано на экране: период (сегодня, вчера, 7, 30, 90 дней, всё время, произвольный диапазон) и кампании (все, активные, завершённые, конкретная). Оба применяются на сервере, в `server/analytics.ts`, один раз — поэтому таблица, график и заголовочное число не могут разойтись, а смена периода действительно другой запрос, а не те же цифры под другой подписью. Рядом с каждым показателем — изменение к предыдущему отрезку той же длины.

Показатели считаются из событий рабочей области. Счётчики демонстрационных кампаний читаются, только если рабочая область объявлена демонстрацией, — так примеры не попадают в цифры настоящего аккаунта.

## Настройки в интерфейсе

Основной путь подключения ящика — **введите рабочий e-mail → определить провайдера → подключить**. SMTP host, порт и TLS живут в «Расширенной настройке» и нужны, только если определить автоматически не удалось.

Платформенные ключи модели, веб-поиска и поиска организаций настраивает суперадмин на экране «Аккаунты» — обычный пользователь не вводит их вообще. Ключи аккаунта остаются запасным режимом на экране «Настройки» → «Интеграции» → «Свои ключи (расширенно)»:

1. **Модель** — ключ OpenAI, модель, необязательный адрес шлюза.
2. **Поиск адресатов** — провайдер (`brave`, `tavily`, `serper`) и ключ.
3. **Google Workspace** и **Microsoft 365** — запасной вариант на случай, если администратор ещё не завёл приложения платформы. Обычно эти шаги можно пропустить.

Сохранённые значения наружу не возвращаются: интерфейс получает только признак «заполнено». Пустое поле при сохранении оставляет прежнее значение. Адрес возврата для OAuth показан прямо в мастере — его нужно указать у провайдера.

## Роли, аккаунты и режим поддержки

Суперадмины подтверждают и блокируют аккаунты; их список задан в `server/accounts.ts` и расширяется переменной `SUPERADMINS`. Обычный суперадмин по-прежнему не читает чужую рабочую область по умолчанию.

Добавлен режим поддержки — «Просмотреть как пользователя». Суперадмин открывает аккаунт и получает представление его рабочей области только для чтения: кампании, адресаты, ветки, аналитика, состояние доменов и почты, журнал. Это не impersonation: маршрут один, он `GET`, он не выдаёт сессию просматриваемого аккаунта, и поэтому ни один изменяющий вызов не может выполниться от чужого имени. Любое привилегированное изменение в будущем должно стать отдельным действием с подтверждением. Каждый просмотр записывается: кто, за кем и когда — журнал поддержки на том же экране.

## Демонстрация и продакшн

Рабочая область нового аккаунта пуста. Демонстрационные кампании, ответы, домены и показатели живут в `demoSeed()` и попадают в аккаунт только если его владелец включил демонстрацию в «Настройках» → «Рабочая область»; там же она очищается. Браузерная демонстрация без сервера использует тот же набор и тот же код правил, веток и аналитики — она показывает продукт, а не его макет.

## Данные и доступ

- Без `DATABASE_URL` сервер хранит состояние атомарно в `data/state.json`; это режим одного процесса.
- При `DATABASE_URL` используется PostgreSQL: состояние рабочей области хранится в JSONB с транзакционной блокировкой. Нормализованная схема и многопользовательская изоляция относятся к следующему этапу.
- По умолчанию API слушает loopback. Публичный адрес включается только вместе с `APP_TOKEN`: без токена сервер не стартует.
- Источник запроса проверяется в `server/origins.ts`. Разрешены: собственный адрес развёртывания (сравнивается с `x-forwarded-*`, поэтому за прокси Railway это работает), `APP_URL`, `PUBLIC_URL`, адреса разработки и всё перечисленное в `ALLOWED_ORIGINS`. Для GitHub Pages задайте `ALLOWED_ORIGINS=https://annetbg-wq.github.io`; см. «Сервер на Railway».
- Пользовательский токен UI хранится только в sessionStorage. OAuth-токены MCP не сохраняются в данных.
- Не добавляйте `.env`, токены, реальные адресаты и содержимое `data/` в репозиторий.

## Три входа в одно ядро

На главной три сценария. Это UX-входы, а не три продукта: кампания, адресат, письмо, ответ и решение по правилам у всех одни и те же.

| Сценарий | Что делает Sendina | Что нужно от вас |
|---|---|---|
| **Сделать всё за меня** | находит компании и адресатов, проверяет источники, пишет персональные письма | описание продукта и подтверждение первой партии |
| **У меня уже есть адресаты** | пропускает поиск компаний, оставляет проверку, персонализацию, правила и ответы | список адресатов с источником и причиной обращения |
| **Настроить вручную** | ничего не берёт на себя | настройка каждого шага самостоятельно |

Короткий путь: **что продаём → какую проблему решаем → чего хотим добиться → где ищем → отправитель → предпросмотр → запуск.** Рынок можно выбрать самому или доверить Sendina — рекомендация настоящая, с объяснением, а не молчаливое значение по умолчанию.

Ключи модели, поиска и поиска организаций пользователь не вводит: их один раз задаёт администратор на экране «Аккаунты». Аккаунтские ключи остаются как запасной вариант в расширенных настройках.

## Поиск организаций

Когда подключён структурированный поиск, исследование идёт от того, что заведомо существует:

**реальные организации → их публичные страницы → оценка соответствия цели → нужная роль → адрес → подтверждение источника → персонализация.**

Google Places — адаптер по умолчанию, сменяемый. Существующий веб-поиск (Brave, Tavily, Serper) не заменён: он работает вторым слоем, которым ищутся страницы контактов и подтверждаются адреса. Механическая защита от выдуманных адресов общая для всех путей: ссылка, которой не было в выдаче, отбрасывается, а адрес сохраняется, только если он дословно встречается в этом источнике.

Автоматический режим выбирает самое сильное доступное доказательство: организации → веб-поиск → предложения модели.

## Контроль перед первой отправкой

У кампании три режима, по умолчанию для нового пользователя — «подтвердить первую партию»:

| Режим | Что говорят правила |
|---|---|
| Подтвердить первую партию | `FIRST_BATCH_APPROVAL_REQUIRED`, пока оператор не подтвердил |
| Полностью вручную | `MANUAL_APPROVAL_REQUIRED` для каждого адресата |
| Полностью автоматически | правила проверяют всё остальное как обычно |

Предпросмотр показывает пять настоящих адресатов: организацию, роль, источник, доказательство, причину выбора и письмо целиком. Он оценивает правила так, как если бы кампания уже шла, — иначе черновик показывал бы «кампания не активна» для всех и скрывал реальные решения. Проблемы самого адресата (нет причины, источник не подтверждён) показываются раньше режима контроля, чтобы обзор их не прятал.

## Единое ядро операций

`server/operations.ts` — единственный слой действий. Интерфейс вызывает его через тонкие маршруты Express, MCP вызывает те же функции напрямую в процессе, без обращения к localhost. Одна проверка схемы, одно решение по правилам, одна запись в журнал — независимо от того, пришло действие из браузера или из ChatGPT.

| Действие | Интерфейс | MCP |
|---|---|---|
| Кампании | Рассылки | `create_campaign`, `list_campaigns`, `get_campaign`, `set_campaign_status` |
| Адресаты | «Найти адресатов», «Импорт JSON» | `find_recipients`, `import_contacts`, `confirm_recipient` |
| Письма | «Подготовить письма» | `prepare_messages` |
| Ответы | Экран «Ответы» | `record_reply`, `exclude_recipient` |
| Метрики | Главная и Аналитика | `get_dashboard`, `get_capabilities` |
| Ящики | Настройки → Почта и домены | `list_mailboxes`, `test_mailbox`, `verify_mailbox`, `sync_replies` |
| Остановка | Настройки → Рабочая область | `emergency_stop` |
| Возможности | Возможности | `research_opportunities`, `list_opportunities` |
| Рынки | Рынки | `research_markets_by_country`, `research_markets_by_niche`, `assess_market`, `list_markets` |
| Избранное | Возможности и Рынки | `save_favourite`, `remove_favourite` |
| Тест из исследования | «Создать тест» / «Подготовить тест» | `create_test_from_research` |
| Ветки переписки | Ответы | `list_threads`, `get_thread`, `set_thread_action` |
| Аналитика за период | Аналитика | `get_analytics` |
| География | селектор локации | `list_locations` |

Отдельного состояния у MCP нет. Поиск, запущенный из ChatGPT, заменяет те же шесть строк, которые покажет экран «Возможности», с теми же идентификаторами; сохранённая из чата возможность появляется в избранном интерфейса; созданный по ней тест — обычная кампания. Это проверяется тестом `tests/connector.test.ts`, который проходит сценарий из ТЗ целиком.

## Поиск адресатов

Два режима, переключатель на экране «Настройки»; по умолчанию выбирается автоматически.

- **Поиск в интернете** — при заданных `SEARCH_PROVIDER` и `SEARCH_API_KEY` (`brave`, `tavily` или `serper`). Модель составляет профиль клиента и запросы, поиск возвращает настоящие ссылки, модель отбирает кандидатов.
- **Предложения модели** — когда поискового ключа нет. Модель предлагает организации и роли, но адреса и ссылки всегда пустые.

Модель не может выдумать адрес или источник, и это проверяется механически, а не обещанием в подсказке:

- `sourceUrl` кандидата должен буквально совпадать с одной из ссылок, вернувшихся из поиска, иначе кандидат отбрасывается;
- адрес сохраняется, только если он дословно встречается в тексте этого результата, иначе поле очищается, а адресат получает статус «не подтверждён»;
- неподтверждённый адресат блокируется правилом `SOURCE_UNVERIFIED` и не может попасть в отправку, пока его не подтвердят через «Подтвердить адресата» или `confirm_recipient` — с настоящим адресом, ссылкой и доказательством.

Повторный поиск не создаёт дублей. Ручной импорт JSON остаётся дополнительным режимом с теми же требованиями к источнику, основанию и причине контакта.

## Подготовка писем

«Подготовить письма» строит черновики и решение по правилам для каждого адресата: причина контакта, источник, статус подтверждения и код решения. Повторный вызов не создаёт дубликаты.

Адресат без конкретной причины контакта получает не персональное, а общее письмо, помечается как похожее на спам и блокируется правилом `CONTACT_REASON_REQUIRED`. Это разные тексты, а не одна и та же рассылка с подстановкой имени.

При переводе кампании в активное состояние выполняется автопроверка повторов: адреса, уже занятые другой кампанией, попадают в отчёт и блокируются правилом `DUPLICATE_RECIPIENT`.

## Подключение почтовых ящиков

Рабочий сценарий — корпоративный ящик на домене организации у **любого** провайдера. Личный Gmail поддерживается, но помечается как вторичный тестовый случай.

Пользователь вводит только адрес. Дальше Sendina сама:

1. Определяет домен и читает MX-записи.
2. Google Workspace или Microsoft 365 → предлагает кнопку OAuth.
3. Любой другой провайдер → подбирает SMTP и IMAP в таком порядке: записи SRV домена (RFC 6186) → известные провайдеры по MX (Яндекс 360, Mail.ru, Zoho, Fastmail, GoDaddy, Hostinger, Beget, Timeweb и другие) → база настроек Thunderbird → обычные имена узлов провайдера.
4. Если ничего определить не удалось — показывает поля вручную: SMTP host/порт/TLS, IMAP host/порт/TLS, пользователь, пароль или пароль приложения.

Определение читает только DNS и ничего не подключает.

### Что проверяется после подключения

Автоматически и подряд, для любого способа подключения:

| Проверка | Что доказывает |
|---|---|
| Вход | учётные данные приняты: refresh token обновляется или SMTP принимает логин |
| Отправка | настоящее письмо с одноразовым кодом ушло через подключённый аккаунт |
| Приём | входящий канал отвечает: IMAP открывает INBOX либо Gmail/Graph отдают список |
| Чтение письма | то самое письмо с кодом прочитано обратно |

Статус «Готов к отправке» появляется, только когда прошли все четыре проверки **и** DNS домена проверен и содержит SPF, DKIM и DMARC. Невыполненные условия показываются списком целиком.

**Проверка DNS подключением не считается.** Идеальные SPF, DKIM и DMARC при неподключённом ящике дают `NOT_CONNECTED`. Отправка без приёма тоже не считается: если письмо ушло, но не вернулось, ящик остаётся не готов.

### Ответы

«Принять ответы» забирает письма из ящика тем же каналом (IMAP, Gmail API или Microsoft Graph) и раскладывает их по кампаниям: адрес отправителя ищется среди адресатов, ответ связывается с кампанией, сохраняются `Message-Id` и `In-Reply-To`. Одно письмо не попадает в журнал дважды. Категория ставится по названным правилам — это заявленная эвристика, а не понимание текста. Ответы видны на экране «Ответы», в аналитике и через MCP (`sync_replies`, `get_dashboard`).

### Секреты

Пароли ящиков и refresh token провайдеров шифруются AES-256-GCM и не возвращаются ни через API, ни в интерфейс. Ключ берётся из `ENCRYPTION_KEY`; если переменная не задана, сервер создаёт ключ сам и говорит об этом на экране «Аккаунты».

### Настройка платформы и подключение пользователем

Это разные роли, и они разделены явно:

- **Администратор** один раз заводит OAuth-приложения Google и Microsoft на экране «Аккаунты» → «Приложения платформы». Адрес возврата для обоих: `https://sendina-production.up.railway.app/oauth/mailbox/callback`.
- **Пользователь** после этого нажимает «Подключить Google Workspace» и проходит обычное окно согласия. Никаких client id он не вводит.

Пока приложения платформы не заведены, интерфейс честно говорит, что это делает администратор, и предлагает подключить ящик как обычный корпоративный. Поля client id остаются в мастере аккаунта как запасной вариант.

## MCP / ChatGPT

Endpoint: `https://sendina-production.up.railway.app/mcp`, транспорт Streamable HTTP.

Встроенный сервер авторизации OAuth 2.1 включается сам, когда задан `APP_TOKEN`, а `OAUTH_ISSUER` пуст. Внешний провайдер не нужен.

| Endpoint | Назначение |
|---|---|
| `/.well-known/oauth-protected-resource/mcp` | Метаданные защищённого ресурса |
| `/.well-known/oauth-authorization-server` | Метаданные сервера авторизации |
| `/oauth/register` | Динамическая регистрация клиента (RFC 7591) |
| `/oauth/authorize` | Согласие оператора, PKCE S256 обязателен |
| `/oauth/token` | Обмен кода и обновление токена |
| `/oauth/jwks` | Публичный ключ подписи |

Подключение в ChatGPT: добавьте коннектор с адресом `https://sendina-production.up.railway.app/mcp`. ChatGPT сам зарегистрирует клиента и откроет экран согласия — на нём нужно ввести **код коннектора** вашего аккаунта, он показан на экране «Настройки». Код привязывает коннектор ровно к одному аккаунту, поэтому из чата видна только ваша рабочая область. Экран согласия следует языку браузера.

Ключ подписи и зарегистрированные клиенты хранятся отдельно от рабочей области (`auth_store` в PostgreSQL либо `data/auth.json`) и не попадают в `/api/state`. Токены не передаются в инструменты и не сохраняются в данных.

Права: `sendina:read` для чтения, `sendina:write` для изменений. Инструменты имеют read/write-аннотации. `MCP_TOKEN` остаётся только для локального клиента без OAuth.

## Реализованные сценарии

- Создание кампании с контекстом, рынком и обязательным целевым событием.
- Импорт JSON-адресатов: email, имя, компания, источник, основание, конкретная причина контакта. Повторный импорт не создаёт дубль в кампании.
- Предпросмотр первых пяти писем; повторный запрос не создаёт дубликаты черновиков. Текст составляется из введённых фактов, без заявления о работе ИИ.
- Ручная регистрация ответа через API; повтор `eventId` не дублирует событие. Отписка и отказ создают глобальное исключение.
- Проверки остановки, состояния кампании, исключения, наличия ответа, основания контакта, домена и общего лимита. Все предпросмотры получают версию решения и причину блокировки.
- Реальная проверка наличия SPF, DKIM и DMARC через серверный DNS. Наличие записей не делает домен автоматически готовым к отправке.
- Подключение ящика у любого провайдера: автоопределение SMTP/IMAP по SRV, MX и базе Thunderbird, ручные поля как запасной вариант, OAuth для Google и Microsoft приложением платформы.
- Четыре проверки после подключения — вход, отправка, приём, чтение тестового письма — и статус «готов» только после всех и проверенного DNS.
- Приём ответов из ящика в единое ядро со связью с кампанией и адресатом; те же данные видит MCP.
- Шифрование паролей и токенов почтовых ящиков в хранилище.
- Единый серверный слой операций: интерфейс и MCP выполняют одни и те же функции, MCP больше не ходит на localhost.
- Поиск адресатов в двух режимах с механической проверкой источника и адреса; неподтверждённые кандидаты не проходят правила.
- Подготовка писем с причиной контакта и решением по правилам; письмо без причины помечается как спам отдельным текстом.
- Автопроверка повторяющихся адресов при переводе кампании в активное состояние.
- Встроенный сервер авторизации OAuth 2.1 с PKCE и динамической регистрацией клиента для коннектора ChatGPT.
- Аварийная остановка. Её снятие не возобновляет кампании автоматически.
- RU/EN для экранов, форм и уведомлений; язык сохраняется, пользовательские тексты не переводятся.
- Аккаунты с входом по одноразовой ссылке, подтверждением суперадминами и раздельными рабочими областями.
- Три сценария запуска поверх одного ядра: ведомый режим, свой список адресатов и ручная настройка.
- Поиск от реальных организаций со структурированным адаптером; веб-поиск остаётся вторым слоем подтверждения.
- Режимы контроля с подтверждением первой партии как правило отправки, а не как подсказка в интерфейсе.
- Пошаговый мастер подключений: ключи модели, поиска и почтовых провайдеров задаются в интерфейсе аккаунта и не возвращаются наружу.
- Переключение языка прямо на экране входа и переход в демонстрацию без сервера.
- Исследование возможностей и рынков одним внутренним механизмом: шесть результатов, оценка 0–100 по формуле ТЗ, считается кодом, а не моделью.
- Избранное для возможностей и рынков; новый поиск заменяет результаты и не трогает сохранённое.
- Свободный выбор географии: страна, несколько стран, регион, город или выбор Sendina — вместо фиксированного списка из шести рынков.
- Ветки переписки: свёрнутая карточка адресата, полная хронология по клику, итог ветки и отметка выполнения следующего действия.
- Аналитика с фильтрами периода и кампаний, считается на сервере из событий рабочей области, со сравнением с предыдущим отрезком.
- Пустая рабочая область у нового аккаунта; демонстрация — отдельный включаемый режим.
- Меню по роли: «Аккаунты» существуют только для суперадминов, и маршруты за ними отказывают остальным.
- Режим поддержки «просмотреть как пользователя»: только чтение, без сессии чужого аккаунта, с журналом обращений.
- Общий путь изменяющих запросов принимает собственный источник развёртывания, поэтому кнопки работают и с Pages, и с самого Railway.

## Что ещё требуется по полному ТЗ

Очередь отправки с защитой от повторов; автоматическое, а не по кнопке, получение ответов; версионированные правила юрисдикций; динамические лимиты по репутации; оркестрация экспериментов и перераспределение объёма; подтверждённые доставки и ценность результата; полноценные workspace/RBAC и нормализованная схема БД вместо JSONB.

Исследование возможностей и рынков намеренно построено на существующих адаптерах — модель, веб-поиск, поиск организаций — с одной структурированной схемой и проверкой ответа. Отдельный crawler, data-platform или knowledge graph не строились: источники можно усиливать позже, не меняя ни UX, ни хранилище.

Сейчас `/api/send` всегда возвращает 409. Это явная граница реализации, а не имитация доставки.

## Сервер на Railway

GitHub Pages отдаёт только интерфейс. Проверка DNS, MCP и общая рабочая область требуют Node-сервера.

1. Railway → **New Project** → **Deploy from GitHub repo** → `annetbg-wq/sendina`. Файл `railway.json` задаёт сборку, запуск и проверку `/api/health`.
2. Добавьте в проект **PostgreSQL**. Railway сам подставит `DATABASE_URL`. Без него состояние лежит в файловой системе контейнера и пропадает при каждом развёртывании.
3. Переменные сервиса:

   | Переменная | Значение |
   |---|---|
   | `APP_TOKEN` | случайная строка; без неё сервер не слушает публичный адрес и не включает OAuth |
   | `ALLOWED_ORIGINS` | `https://annetbg-wq.github.io` |
   | `PUBLIC_URL` | `https://sendina-production.up.railway.app` |
   | `DATABASE_URL` | подставляет Railway вместе с плагином PostgreSQL |
   | `APP_URL` | `https://annetbg-wq.github.io/sendina/` — куда ведут ссылки для входа |
   | `SYSTEM_SMTP_HOST`, `SYSTEM_SMTP_USER`, `SYSTEM_SMTP_PASS` | системная почта; без неё войти сможет только суперадмин через журнал |
   | `SYSTEM_SMTP_PORT`, `SYSTEM_MAIL_FROM` | необязательно |
   | `SUPERADMINS` | необязательно: дополнительные суперадмины через запятую |

   Ключи OpenAI, поиска и почтовых провайдеров сюда не входят: их заполняет каждый аккаунт в интерфейсе.

   `PORT` и `HOST` задавать не нужно: `PORT` приходит от Railway, а публичный адрес включается по `RAILWAY_ENVIRONMENT_NAME`.
4. **Settings → Networking → Generate Domain**. Получится адрес вида `https://sendina-production.up.railway.app`.
5. В GitHub: **Settings → Secrets and variables → Actions → Variables** → `VITE_API_URL` = адрес из шага 4 (уже задан). Переменная читается при сборке, поэтому после её изменения нужен новый запуск workflow «Deploy GitHub Pages». Это переменная сборки, она попадает в браузер — секреты в неё класть нельзя.
6. Откройте сайт, на экране «Настройки» введите `APP_TOKEN`. Токен хранится только в sessionStorage вкладки.

Без `VITE_API_URL` сайт остаётся демонстрацией в браузере: данные не покидают устройство, проверка DNS и MCP недоступны. Сохранённый в браузере адрес сервера имеет приоритет над `VITE_API_URL`; пустое значение выбирает демонстрационный режим.

## Публикация

Workflow `.github/workflows/pages.yml` проверяет тесты, собирает приложение с `/sendina/` в качестве base path и публикует `dist` через GitHub Pages. Необязательная repository variable `VITE_API_URL` задаёт адрес отдельного API. Секреты нельзя помещать в переменные `VITE_*`: они попадают в браузер.
